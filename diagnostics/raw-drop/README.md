# 720×480 YUYV 60fps 接收诊断

2026-10-04，vivo V2338A、U4 4K60。用户已 reset 高质量 YUV→RGB 模式，本次不恢复该改动。正在运行的 APP PID 为 21283。

## 当前证据

原始日志和系统 trace 保存在忽略的 `build/perf-diagnostics/raw-drop/`。两次日志快照联合分析，约 460 秒的稳定阶段结果：

| 阶段 | 采样时间（秒） | 新增帧 | 平均 FPS |
| --- | ---: | ---: | ---: |
| UVC 发布 | 460.032 | 27212 | 59.1524 |
| JNI 视频回调 | 460.504 | 27240 | 59.1526 |
| Kotlin 接收 | 460.571 | 27244 | 59.1527 |
| GPU 编码输入 | 460.571 | 27244 | 59.1527 |
| 编码输出 | 460.571 | 27244 | 59.1527 |

各阶段日志采样时间不同，不能直接相减累计帧数；接收／渲染／编码之间只有约 2～3 帧稳定的流水线差额，没有持续增长的缺帧差额。首尾完整图像字节差额等于帧数差额 × 691200，符合 720×480 YUYV。

稳定阶段 `sequenceGaps=0`、`badHeaders=0`、`transferErrors=0`、`submitErrors=0`、`bulkRawRepairs=0`。`errorPayloads=74`、`fidWithoutEOF=1` 在所有快照保持不变；日志环形缓冲已没有启动阶段，不能确定初始错误的原因，但这些错误不是持续的帧率损失。现有日志没有逐帧长度验证，完整字节差额也不能排除采样前的短帧。

10 秒 sched／IRQ／频率 trace 中，USB 事件线程 TID 31396 约使用 1836.7 ms CPU，唤醒／再次运行等待中位数 0.015 ms、P95 0.066 ms、P99 0.350 ms、最长 3.087 ms，仅一次超过 3 ms。此记录有采样开销；唤醒延迟不能等同于 USB 请求队列空置时间，更不能单独证明无主机瓶颈。

Android USB 描述显示视频 Bulk 端点 0x82 的 max_packet_size=512，这符合 High-Speed USB 2.0 的端点形态。sysfs `speed` 在 shell 和 run-as 下均不可读，尚无当前运行版本的内核连接速率读数。不要把描述中的 `bcdUSB` 当作实时连接速率。

该模式的纯图像吞吐需求为 720×480×2×60 = **41.472 MB/s、331.776 Mbps**，另有 UVC 头、音频和总线协议开销。USB 2.0 的 480 Mbps 是线路速率，实际 Bulk 图像吞吐较低，当前模式有带宽压力；USB 2.0 仍不能仅凭这一计算判定必然无法实现该模式。

源码配置 8 项异步请求，每项采用设备协商的 `dwMaxPayloadTransferSize`。旧的 U4 记录为 16384 字节；当前稳定日志每帧约 43 次返回，也与此吻合，但协商启动日志已经被覆盖。若每项确为 16 KiB，则总队列为 128 KiB，按图像吞吐只能覆盖约 3.16 ms。增加请求数量可能降低调度间隙影响，但不会提高总线或采集卡本身的极限。本次没有据此改动请求数量或解析行为。

采样时系统 Thermal Status=4（CRITICAL），skin 约 48°C。实时 cooling device 读数未显示 CPU／GPU cooling 强度，不能从 status 单独断定已经降频；它是后续冷机对照的变量。

## 新增诊断

- 启动时在已获授权的 USB Host fd 上调用只读 `USBDEVFS_GET_SPEED`，直接记录内核速率枚举（3=480Mbps、5=5Gbps、6=SuperSpeedPlus）。同时记录协商间隔／时钟和 Bulk 请求大小／队列字节数。
- 按固定源帧尺寸统计 `rawShort`／`rawLong` 和被帧缓冲上限截断的字节数。只观察，不改变发布／解析行为。
- 每 5 秒记录主机完整帧间隔 min／avg／max、超过协商间隔 1.5 倍的次数，以及设备 PTS tick 差值 min／avg／max。PTS 按 32 位无符号差值处理，区分缺失、重复和回退，零值及自然回绕有效；不跨缺失 PTS 的帧计算差值。设备可能错误报告时钟，必须同时核对 raw tick，不能直接将 PTS 推算 FPS 当真值。
- 记录未完成帧期间，从上一次处理／重新提交结束到下一次回调的间隙、超过 1／3 ms 的次数和交换帧时等待回调锁的最大时间。间隙也包含设备／总线等待，不能直接解释成主机队列耗尽。
- Kotlin 记录原始队列淘汰、转换失败、GPU 未提交编码帧的次数和队列长度，进一步排除下游损失。

除了原有序列／累计异常计数，帧间隔、PTS tick 分布、接收间隙、锁等待和吞吐是每 5 秒窗口统计。PTS 缺失／重复／回退、帧尺寸及下游失败计数是会话累计值。

验证：62 项 JVM 单元测试通过；在手机独立原生进程运行 `uvc_payload_test` 通过，涵盖全部已有 MJPEG／固定尺寸源粘包用例，并新增 PTS 零值／回绕、重复、回退、缺失、短帧和截断计数验证。当前应用未停止或覆盖安装。

## 后续对照

安装诊断版后先保持同一 YUYV 模式，采样至少 30 秒，核对协商间隔、实际 USB 速率、PTS 和各阶段丢帧计数。之后可用相同尺寸／帧率的 NV12（31.104 MB/s，减少 25% 图像流量）做对照；原有设备描述支持该模式。如果稳定接收率恢复，应结合 PTS／接收间隙判断带宽压力；它仍不单独区分采集卡的格式实现与主机 USB 吞吐。不要用编码码率替代 USB 源数据吞吐。

## 新版真机对照结果

用户手动安装新版并运行推流，PID 21653；随后按要求切换 NV12，保持 720×480、60fps。原始数据位于 `build/perf-diagnostics/raw-drop/diagnostic-yuyv-live.log`、`diagnostic-nv12-live.log` 和后续补采日志。

内核 fd 的实测 `kernelSpeedEnum=3` 确认当前链路为 **USB 2.0 High-Speed 480 Mbps**。两个模式均协商 `interval100ns=166666`（名义 60.00024fps），clockHz=27000000，Bulk 端点 packetBytes=512，8×16384 字节请求，queuedBytes=131072。YUYV 固定帧为 691200 字节，NV12 为 518400 字节。

| 稳定阶段 | YUYV | NV12 |
| --- | ---: | ---: |
| 日志区间 | 22:42:04～22:43:04 | 22:44:39～22:46:19 |
| UVC 发布平均 FPS | 59.2941（60.006秒） | 59.9404（100.066秒） |
| JNI 视频回调平均 FPS | 59.2927 | 59.9409 |
| 渲染／编码平均 FPS | 59.2906／59.2906 | 59.9369／59.9469 |
| 设备 PTS 推算 FPS | 59.2936 | 59.9388 |
| USB 视频实际接收量 | 约41.015 MB/s | 约31.096 MB/s |
| 主机帧间隔超过25ms次数 | 39／13个5秒窗口 | 1／21个5秒窗口 |
| 原始队列淘汰／时间戳跳帧 | 0／0 | 0／0 |

表中的平均帧率用同类累计计数的首尾差值除以其日志时间差，PTS 使用各窗口样本数加权的 tick 差值。窗口统计与首尾差值的统计区间略有不同，不应把渲染／编码的约0.01fps差异理解为持续增减帧。NV12 的稳定 PTS 常见差值是450459／450460 tick，对应约59.94fps；它虽名义协商60fps，设备稳定输出实际上更接近NTSC帧率。

YUYV 22:41:29～22:41:34曾出现完整窗口 PTS 差值恒为450001 tick、接收约60fps，说明当前USB2链路并非在任何条件下都无法传输该模式。持续运行后部分设备PTS间隔增大，同期主机帧率降至约59.3。NV12把数据和请求处理负担降低约25%后恢复稳定59.94，支持 **高吞吐采集／USB传输路径受负载影响** 的判断，而非编码器或平滑时间戳在持续丢帧。源设备的PTS也可能在USB回压下改变，不能因PTS变慢就认定与主机USB读取无关。

开流及22:41:36～22:41:49期间，YUYV出现2485个ERR payload、7个短帧、25592字节截断，转换失败7帧；之后这些计数在稳定观察中没有继续增加。可见原始数据结构为`0C CC/CD/CE/CF`并包含重置到0／逐帧计数的PTS／SCR，部分内容为黑场；这符合设备报告源失锁／重锁或错误状态的形态，不是已知MJPEG粘包导致的伪头，但没有输入侧记录，尚不能确定该阶段触发原因。不能将这些启动／瞬时错误混入稳定阶段帧率归因。

NV12有1个开流短帧／转换失败及149个ERR payload，随后保持不变，没有持续新增坏包／短帧／粘包修复。两种格式都没有transferErrors、submitErrors或sequenceGaps增长。

后续独立补采22:46:09～22:46:39：UVC发布／JNI回调均为1800帧÷30.030秒=59.9401fps，接收／渲染／编码同为1800帧÷30.028秒=59.9441fps；7个窗口中没有主机帧间隔超过25ms，设备PTS仍对应59.9388fps，吞吐约31.0961MB/s。NV12稳定恢复结果再次得到验证，初始错误计数没有增长。

结论：当前重点应落在高吞吐下的采集卡／USB2传输实现和主机接收调度，而不是增加编码缓存或改时间戳。仅改变源格式的对照不能进一步区分总线实效带宽、采集卡固件／内部缓冲及8项请求的队列覆盖能力；本次未宣称已证明硬性USB2带宽上限或读取队列耗尽。若继续优化YUYV，应保持模式不变做更深Bulk请求队列的对照，而不是直接增加单次读取长度（这会改变已有UVC payload边界假设）。

实际可用方案：当前模式使用NV12能够稳定接近59.94fps，但YUYV的4:2:2源色度会变成NV12的4:2:0，垂直色度分辨率降低。需要保留4:2:2时应继续优化／对比YUYV读取，或使用真正支持USB3的完整设备／主机链路。编码码率不改变上述USB源吞吐。

## 界面显示当前 USB 接收速率

用户要求增加当前传输码率显示。预览、录像和推流时均显示 `USB 视频接收：248.8 Mbps · 31.10 MB/s`，约每秒更新一次，首个完整采样窗口前显示“统计中”。原有串流码率仍表示编码输出的发送速率。

接收计数在 libuvc 完成回调、UVC 解析之前累计端点实际返回的字节，包含 UVC 头和被拒绝的 payload，独立于帧发布／解码／队列淘汰。Bulk 使用 actual_length；ISO 使用各 packet 的 actual_length。统计不包含音频端点或 USB 总线协议开销，不能将它作为总线线路利用率。计数使用原子读写，采样时间使用主机单调时钟；录像统计查询与 nativeClose 共用生命周期锁，空闲预览在持有 native 句柄的同一工作线程采样。
